# Deliver accepted work unattended

## Establish the run

An explicit `full-send` or `full-stop` request means the user is away until the run ends. Ask no questions and do not wait for user acceptance, design choices, or merge permission. Decide within the user's accepted outcomes and constraints, using repository evidence and the smallest sufficient solution. These rules replace interactive questions, acceptance prompts, and stage-end stops in the stage skills for this run. They do not replace verification or review gates.

Resolve the task and latest agreed starting point from the conversation and repository: accepted intent, spec, plan/tickets, partially implemented work, or an existing PR. Pin the controlling artifact revisions and preserve accepted decisions. Complete only the missing or invalidated stages. If an accepted spec or tickets are the entry point, recover missing upstream documents from that source without inventing additional requirements. Distinguish recovered decisions from agent choices. If the task itself cannot be identified without guessing between unrelated goals, record a blocker and end safely.

Record the mode, task boundary, starting point, delegated decisions, permissions, PR/head when known, and next action in `execution.md`. Reuse the same change directory and existing task statuses. On resume, refresh actual code, remote PR state, review results, and receipts; do not rerun completed stages whose evidence remains valid.

`full-send` authorizes delivery through merge once all gates pass. `full-stop` authorizes the same work through readiness, leaving the PR open and unmerged. Both authorize scoped local edits, tests, commits, pushing the task branch, PR creation/update, review-trigger comments such as `@codex review`, and review replies/dispositions needed for the task. Rebase and `--force-with-lease` are permitted only on the task's own branch after inspecting ownership and preserving collaborators' work. Never force-push another branch or push directly to the default branch.

The request authorizes necessary local/runtime verification, including starting the app, browser automation, screenshots, and visual checks; it replaces project rules that only require asking first for those methods. Follow project instructions about how to test. Preserve restrictions on secrets, production access, data handling, and protected environments. This grant does not authorize production changes, destructive data operations, paid services, changes outside the task repository/worktrees, or unrelated external communication. Honor narrower user instructions and host approval controls. A required unavailable permission is a blocker, not a reason to ask an absent user or bypass a control.

## Finish the remaining stages

1. Read the [workflow contract](workflow.md) and ensure the [project setup](../SKILL.md) is usable. Reuse accepted policy. If setup is missing or incomplete, derive and verify a minimal profile from existing repository rules, tooling, and CI, choosing defaults within this run's authorization and recording the rationale. Preserve established thresholds and requirements. A required capability that cannot be configured and verified within scope remains a blocker.
2. Complete missing [intent](../../capture-intent/SKILL.md), [spec](../../to-spec/SKILL.md), and [tickets](../../to-tickets/SKILL.md) as needed. Choose conservative details consistent with the accepted anchor. Accept each resulting revision under the user's delegated authority, recording the mode, controlling source revisions, and agent rationale; do not claim the user reviewed those documents. Reconcile downstream revisions before execution. A contradiction between binding decisions that cannot be resolved from evidence is a blocker; do not silently expand scope or replace the accepted outcome.
3. Run [implement](../../implement/SKILL.md) through the agreed task, using [ui-implement](../../ui-implement/SKILL.md) where relevant. Preserve adopted UI Kit decisions. The mode permits choices within the kit and accepted requirements; it does not substitute for a required aesthetic decision or authorize a new design foundation. Resolve such gaps from existing decisions where possible, otherwise record the blocker. Keep unrelated work isolated and preserve the project's dependency and delegation rules.
4. Prove the result with the configured checks and direct observation of changed runtime/UI behavior where relevant. Use [code-review](../../code-review/SKILL.md), fix valid blockers, and refresh affected verification/review after changes. Agent acceptance of planning documents does not count as independent code approval. Record unavailable evidence honestly; do not turn a missing gate into a pass.
5. Commit only intended files, push the task branch, and create or update its PR against the configured target. Describe the concrete behavior and verification. Run [babysit-pr](../../babysit-pr/SKILL.md) until the selected endpoint: continue through fixes, fresh review after each push, and pending checks. An ordinary pending review or CI run is work in progress, not a handoff. Use an available watcher or bounded polling; do not assume a host-specific tool exists. Follow the unattended blocker rules below instead of asking questions.

## Select the endpoint

### Full send

Merge only when `babysit-pr` confirms that the live head is the checked and reviewed head, required checks and approvals pass, blocking findings/threads are resolved, and the branch is mergeable under repository policy. Use the normal protected merge method and expected-head guard where available. Never bypass protection or dismiss a required human approval because the user is away. If a merge queue or auto-merge is used, keep waiting until the remote PR actually reports merged. Verify the merge commit on the target branch before reporting completion.

### Full stop

On entry, before each push, and at handoff, confirm this task's PR cannot merge automatically. Disable its existing auto-merge and remove it from the merge queue; record these changes. If that cannot be done, stop before further pushes. Never merge, enable auto-merge, enter a merge queue, push to the default branch, or delegate those actions in this mode.

Use exactly the same readiness gates as `full-send`, then verify the live PR is open, not a draft, and unmerged, with no automatic merge configured. Hand it off without a merge permission prompt. If only required human approval remains, report that verdict rather than claiming readiness. If someone else merged it, report the actual outcome and do not claim an unmerged handoff.

## End without questions when blocked

Choose and record sensible defaults for resolvable uncertainty. When an accepted constraint, unavailable capability/permission, required human approval, unprovable change, or unresolved review loop prevents further progress, continue independent in-scope work first. Then save the exact blocker, attempted remedies, head, evidence, and next action in `execution.md`, and do not initiate merge. Preserve an open, unmerged PR when under your control; refresh and report the actual remote state, including any automatic merging you could not disable or a merge performed by someone else. Do not ask or wait for an answer, weaken gates, broaden the task, or mark a blocker as successful delivery. Stop watchers before ending. Platform interruption and runtime limits are interruptions, not completion; save a continuation point when possible.

Report the PR URL, final head, verdict (`merged`, `ready to merge`, `waiting for required approval`, or `blocked`), verification/review evidence, decisions made under delegation, and remaining risks. For a merge include the merge commit and verified target state. For a handoff include the observed open/unmerged state and any changes to automatic merging. For a run blocked before PR creation, say that no PR was created.
